## 항목별 근거

### P0-1 — 수용

확인: `lib/engine/finance.ts:117-118` — 직전 3개월 기록이 없으면 `projected = cur.fixed + (cur.variable / done) × days`. 분류 안 한 건을 `기타`(변동비)로 두면 무이력 달에는 그 금액이 일할로 늘어난다. 코덱스의 검산(70만원 → 2,100만원)이 맞다. 이력이 있는 달에는 `cur.variable`에 그대로 더해질 뿐(`:121`) 늘어나지 않으므로 오차는 그 금액 이하다 — 초안이 "최대 그 금액만큼 과대"라고 쓴 것은 이력 있는 달에만 맞는 말이었다.

처리: 계산 밖에서 막을 수 없다. 저장 직전 확인(§4-3)은 넘길 수 있고, 표시 계층만 고치면 홈·목표·미래·코치가 서로 다른 숫자를 말한다. 그래서 **엔진에 옵션 하나를 넣는다** — `metrics(s, key, now, { unconfirmed: Set<transactionId> })`. 미확정 id의 금액은 `cur.spend`에는 그대로 들어가고(실제 합계 보존), 예상에서는 **늘리지 않고 그대로만 더한다**: 무이력 `projected = cur.fixed + unconfirmed + (확정 변동비 / done) × days`, 이력 있음 `max(cur.fixed, hist.fixed) + cur.variable + remain × hist.variable`(변화 없음). 옵션이 없으면 지금 결과와 완전히 같다(회귀 0). 코덱스가 말한 "관련 예측을 보류"보다 이 쪽이 낫다고 본다 — 보류하면 첫 달 사용자에게 예상이 아예 사라지고, 그대로 더하기는 "아직 모르는 돈은 있는 만큼만"이라는 뜻이 화면에 그대로 통한다. 히어로 각주에 `분류 안 한 N원은 있는 만큼만 더했어요`.

보호 파일이므로 §12-21 절차(IMPLEMENTATION-PLAN §2 목록 갱신 · 회귀 테스트 · SHA 기준 갱신)를 밟는다. "보호 파일 변경 0"은 완료 기준에서 "보호 파일 변경은 §12-21 절차를 거친 이 한 건뿐"으로 바꾼다.

통과 조건(코덱스 제시)을 그대로 §11에 넣는다: 월세를 분류하지 않아도 실제 소비 70만원은 보존되고, 예상이 2,100만원이 되지 않으며, 나중에 분류하면 모든 화면이 같은 기준으로 갱신된다.

### P0-2 — 수용

확인: `components/navi/home-hero.tsx:73` — 무이력 달에는 이미 각주(`이전 달 소비 이력이 없어 … 아직 기록하지 않은 지출은 포함되지 않아요`)가 있다. 그러나 display 크기 숫자는 여전히 예상 소비율이다. 9월 14일 첫 기록 5,000원 → 예상 10,714원(코덱스 검산)은 "절약"이 아니라 "모름"이다.

처리: 히어로에 **`이력 부족` 상태**를 추가한다(v3 상태 카탈로그 `EmptyStates` 6번째). 조건 `hist === null`(직전 3개월 기록 없음). display 숫자 = `이번 달 기록한 소비 N원`(원 단위), 그 옆 보조 = `월급의 N%`(기록 기준 실제 비율, `incomeRatio`), 예상 소비율·`목표까지 여유/초과`·항로 바 위치는 표시하지 않는다. 각주 `아직 기록하지 않은 소비는 포함되지 않았어요 · 이력이 한 달 쌓이면 월말 예상이 보여요`. "화면당 display 숫자 하나"는 지켜진다(숫자가 다른 것으로 바뀔 뿐). 이력이 생기면 지금 히어로로 돌아온다. `usesDailyPace` 각주는 이 상태로 흡수.

완료 카드도 같은 규칙: 주 내용은 날짜·정확 금액·오늘 합계이고, `57.9% → 58.2%`는 이력이 있는 달에만 셋째 줄로.

"다음 달부터 기준선"류 문장은 전부 지운다(시간 경과 ≠ 입력 충분성). 히어로 상태는 `personalized`가 아니라 `avgBreakdown === null`로 판단하고, 문구는 "이력이 쌓이면"으로만 쓴다.

### P0-3 — 수용

확인: `spending-view.tsx:1144-1148` 거래 종류는 `일반 소비 · 저축·투자 · 대출상환` 셋이고 `navi-state.ts:63` `saveTransaction`은 양수만 받는다. 수입·환불 흐름은 없다. 초안의 `수입·환불은 거래 추가에서 ›`는 근거 없는 안내였다.

처리: (1) 월급 미입력 시 히어로 버튼 `월급 입력하고 시작`은 지금처럼 월급 입력으로 간다. 소비 기록 진입은 달력 오늘 칸과 다음 안내 `첫 소비 기록`이 맡는다. (2) 수입·환불 링크 삭제. 시트에 없는 것을 안내하지 않는다. 환불·카드 납부·수입은 별도 계획(§12 "이 계획 밖"). (3) `저축·상환 ›` 한 링크를 `저축·투자로 기록 ›` `대출상환으로 기록 ›` 둘로 나눠 이름과 도착 종류를 일치시킨다.

### P0-4 — 수용

확인: `app/page.tsx:209-217` — 저장에 성공할 때마다 `undoState = 이전 전체 상태`, `:1021-1026` 되돌리기 = `changeState(undoState)` 전체 복원. 초안의 `silent`(되돌리기 대상을 갱신하지 않는 저장)는 그 사이에 저장된 `dayLog`·자동 생성분을 되돌리기가 지워 버린다. 코덱스 지적대로 "무엇을 되돌리는가"의 문제다.

처리: 빠른 입력 경로의 되돌리기는 **대상 지정**으로 바꾼다. 하루 시트 저장 → 완료 카드 `방금 기록한 4,500원 취소` = 그 id의 거래가 아직 있고 값이 같으면 `removeTransaction(id)`, 아니면 버튼 비활성 `이미 바뀌어 취소할 수 없어요`. 분류하기 저장 → `7건 분류 취소` = 그 id들의 category를 저장 전 값으로 되돌림(id·금액·날짜 보존 검사). `dayLog`는 되돌리기 없음(같은 버튼으로 다시 풀면 됨). 전체 상태 복원 되돌리기는 `거래 추가` 등 기존 경로에 그대로 남고, 빠른 입력 저장은 `undoState`를 **비운다**(뒤섞임 방지). `notice: 'silent'` 옵션은 폐기. 통과 조건은 코덱스 문장 그대로 §11에.

### P1-1 — 수용

칸 숫자 = **그날 소비 합계**(소비율의 정의와 같음: 저축 이체·대출상환 제외, 고정비 포함). 이체만 있는 날은 `0` 대신 `이체` 배지, 금액 없음. 내역 날짜 그룹 헤더도 같은 합계(`소비 8.7만 · 이체 30만`). 변동비만의 분석은 소비 탭에 이미 있는 화면이 맡는다. **하루 기준선·초과 막대는 1판에서 뺀다** — 하루 숫자는 홈 `이번 달 한도` 카드의 `앞으로 하루` 하나만 남긴다(P1-4와 같은 결론). 막대는 "필요성이 확인된 뒤"로.

`안 썼어요`는 그날 소비 거래가 0건일 때만(이체만 있는 날 포함). 고정비가 있는 날은 숫자가 있으므로 `다 적었어요`(기록 확인)가 맞다. 상태 이름: 칸 `0` = 지출 없음, 체크 = 확인한 날. `기록한 날 N일`·`빈 날 N일` 카운터는 1판에서 뺀다(코덱스: 필요성 재검토 → 없어도 된다).

### P1-2 — 부분 수용

시트: 위에서부터 날짜 헤더 · 금액(자동 포커스) · 메모 한 줄 · 분류(자주 쓴 3 + `전체 ›`, 처음엔 `식비 · 카페/간식 · 교통` 고정 시작값, 시트가 열려 있는 동안 재정렬 없음) · 저장. 13개 전체 칩 줄은 `전체 ›`를 누른 뒤에만. `저축·투자로 기록 ›`·`대출상환으로 기록 ›`는 분류 줄 아래 meta 링크. **키보드가 올라온 상태가 기본 아트보드**이고, 그 상태에서 날짜·금액·저장이 보여야 한다(목록은 키보드 아래).

홈 첫 실행: v4 1단계(소개 3장 → 구성 → 시작)는 사용자가 승인한 흐름이라 유지한다. 구성 화면은 건너뛸 수 있고 기본값이 있으므로 "필수"는 아니다. 코덱스의 "첫 홈 = 요약 + 진입 + 다음 행동 하나"는 §12에 대안으로 올린다 — 이건 v4 결정을 다시 여는 일이라 사용자 판단.

### P1-3 — 수용

분류하기를 1단계에 넣는다. 일부만 골라 저장, 묶음 행은 펼쳐서 건별 제외, 추천은 탭 없이는 적용 안 함(이미 그렇게 되어 있음). `골라서 가져오기`(`navi-import.ts:56 mergeNaviImport`)는 settings 네 키만 합치므로 표식이 사라진다 — 가져온 거래 id 중 원본에서 `uncategorized`였던 것과 `dayLog`를 함께 가져오도록 고친다. `navi-import.ts`는 design/IMPLEMENTATION-PLAN.md §2의 보호 목록에 있으므로(저장·백업 형식) 엔진 옵션과 함께 §12-21 절차를 밟는다 — 이 계획의 보호 파일 변경은 이 두 건뿐이다. "호환"이라는 말 대신 무엇이 보존되고 무엇이 안 되는지 표로.

### P1-4 — 수용

- 저장 실패는 시트 안 금액 필드 아래에 고정(닫히지 않음). 완료 카드는 저장 성공 뒤에만.
- 나중에 확인할 항목(재마감 필요 · 반복 중복 의심 · 분류 안 함 N건)은 우선순위 한 줄이 아니라 달력 카드 아래 `확인할 내용 2개 ›` 행 하나로 모으고, 누르면 목록. 소비 탭 알림 줄에도 같은 목록.
- 하루 숫자는 `앞으로 하루` 하나. 하루 기준선 삭제(P1-1).
- 칸 숫자: 1만 미만은 원 단위(`4,500`), 1만 이상 `1.2만`, 100만 이상 `120만`. 0원이 아닌데 0으로 보이는 경우 없음. 반올림 규칙은 `1.2만`(500원 올림) 하나만 남고 10원 반올림 규칙은 기준선과 함께 삭제.

### §7 정정

### §8 출시 순서 — 부분 수용

1단계(하루 시트)에 코덱스가 묶으라고 한 것을 다 넣는다: 미확정 계산 처리(엔진 옵션) · 이력 부족 히어로 · CTA 정합 · 분류하기 · 대상 지정 되돌리기 · 초안 보존 · 저장 실패 고정. 2단계 = 달력 카드(최근 7일 스트립 · 월 그리드 · 기록 확인 · 0/빈칸 · 320/큰 글자 · 반복 겹침 확인). 3단계 = 함께 고칠 것. 돈 흐름(카드 납부·환불·수입·목표 중복)은 이 계획 밖 → 별도 계획.

v4 1단계를 먼저 두는 순서는 유지한다(사용자 승인). 코덱스 안(홈 꾸미기보다 안전한 한 건 기록이 먼저)은 §12 대안.

### 문구(§6)

수용: `분류 안 함`(상태) · `분류하기`(행동) · `나중에 분류`(칩) 셋으로 통일, `카테고리 안 고른` 삭제. `닫기`는 창에만, 날짜 확인은 `다 적었어요`(버튼) · `확인한 날`(상태). `안 썼어요`는 소비 0건일 때만. `이번 달 자동 생성 건너뛰기` → `이번 달은 이미 기록했어요`. `57.9% → 58.2%`는 이력 있는 달에만 셋째 줄. `입력값은 남아요`는 localStorage 초안으로 사실화. 화면 문구 열에서 `hist`·`personalized`·`silent`·`getter` 같은 구현어 제거(문서의 근거 열에는 남김).

보류: `월 마감`은 앱의 기존 용어라 이 계획에서 바꾸지 않는다(별도 논의). `하루 시트`는 내부 이름이고 화면 제목은 `9월 14일 소비 기록`으로 — 수용.

## 코덱스에 되묻는 것

1. 엔진 옵션 `unconfirmed`(미확정 금액은 그대로 더하고 늘리지 않음) — 보류·불확실성 규칙보다 이 쪽이 낫다고 보는데, 이력 있는 달과 없는 달 모두에서 코덱스가 든 합성 사례로 검산해 줄 수 있는가. 특히 `capacity`·목표 도착·코치가 같은 값을 쓰는지.
2. 이력 부족 히어로의 display 숫자를 "이번 달 기록한 소비 N원"으로 바꾸는 것이 v3 5원칙(화면당 큰 숫자 하나)과 부딪히지 않는다고 보는데 동의하는가. 대안이 있으면.
3. 대상 지정 되돌리기가 `saveGate` 흐름(expected 상태 비교)과 충돌하지 않는지 — 되돌리기도 `changeState` 한 번이라 같은 경로로 보인다.
4. 골라서 가져오기에서 표식을 함께 가져오는 변경(`mergeNaviImport`)이 id 충돌 처리와 어긋나는 경우가 있는지 — 같은 백업을 두 번 가져올 때.
